三個架構方案

選擇最適合你的架構方向

需求總結

從社群 app（IG、FB、YT、抖音）分享連結 → 自動擷取 metadata + AI 摘要 → 純文字筆記 + 標籤 → 多種瀏覽方式 → 本地儲存 → Flutter 練習

A

全本地架構 ⭐ 推薦

AI 呼叫直接從手機端發出，資料全存本地 SQLite。不需要後端伺服器。

社群 App → 分享連結 → Flutter App
  → 手機端 HTTP 抓 metadata
  → 手機端直接呼叫 AI API（OpenAI / Claude）
  → 存入本地 SQLite

Pros

  • 架構最簡單，專注練 Flutter
  • 零伺服器成本
  • 之後加雲端同步不衝突

Cons

  • API key 存手機端（個人用 OK）
  • 某些平台 metadata 爬取可能受限
B

輕量後端架構

用小後端處理爬取和 AI 呼叫，Flutter 只做 UI 和本地儲存。

Flutter App → 發送連結給後端 API
  → 後端爬取 metadata + 呼叫 AI
  → 回傳結果 → 存入本地 SQLite

Pros

  • API key 安全放後端
  • 爬取 metadata 更穩定
  • 可快取，相同連結不重複處理

Cons

  • 需架設後端，不純粹練 Flutter
  • 有伺服器成本
C

混合架構

metadata 手機端抓，AI 呼叫透過 Cloud Functions 轉發，不需完整後端。

Flutter App → 手機端抓 metadata
  → Cloud Function 轉發 AI API 呼叫
  → 結果存本地 SQLite

Pros

  • API key 不暴露在手機端
  • Cloud Functions 免費額度夠用

Cons

  • 仍需設定雲端服務
  • 比方案 A 複雜
